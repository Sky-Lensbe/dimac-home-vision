# AGENTS.md

- Woningscan prices, product texts and the drone option live only in `supabase/functions/_shared/quickscan/catalog.ts` (no imports), re-exported by `src/data/woningscan.ts`; site, Quickscan recommendation and tests read from there so prices never drift.
- Contact, renovation and Woningscan forms use contact-submit: validate and persist to admin-only contact_submissions before provider sends; server derives package prices from catalog, idempotency keys prevent duplicate emails, and UI distinguishes saved requests from mailbox delivery.
- Confirmed projects live in `src/data/developments.ts`; missing images and descriptive fields remain optional so incomplete records never require invented content. When empty, pages show the development approach instead of cards.
- Indexing is off unless `VITE_ALLOW_INDEXING=true` (PageSEO forces noindex; robots.txt disallows) because the site is not live yet.
- Analytics events go to `window.dataLayer` via `track()`; never include personal data, and a mailto handoff is not a sent message.
- Do not put lead-qualification/scoring logic in frontend code; it belongs behind a secured backend.
- Quickscan rules live only in `supabase/functions/_shared/quickscan/engine.ts` (no imports), shared by browser and server; the server always recomputes. Stored reports are immutable snapshots shown via `src/lib/quickscanSnapshot.ts`, which must never import the engine so old reports are never silently recomputed.
- Quickscan apartment routes use separate question IDs (e.g. Q04A) for private parts; answers whose origin is only common parts (`commonOriginQuestions`) are stripped via `privateSignals()` before private scoring and attention points, and private/collective safety flags are computed separately so the same SAFE-ID from both origins is shown twice, never masked.
- Quickscan submissions persist through the single `quickscan_register` database function (one transaction, advisory lock per report number) called from `_shared/quickscan/persist.ts`, so failures roll back fully and concurrent duplicates yield one record; an unconfirmed outcome gets a neutral message, never a false guarantee.
- Quickscan email recipients are decided only by `supabase/functions/_shared/quickscan/mail-policy.ts`; test mode is a code constant with a server-side allowlist so it can never switch to production automatically.
- Operational copy addresses are centralized in `_shared/mail.ts`; Quickscan PDF copies share the customer message via BCC, and internal notifications use one multi-recipient send so idempotency keys never conflict.
- Quickscan tables allow no anonymous access; inserts go through the service-role function and only `has_role(admin)` users can read, so lead data is never public.
- Quickscan reports are composed by `_shared/quickscan/report.ts` (engine + catalog, one-way dependency) for browser and server; need-led recommendations require corroborating technical domains, not counts of selected works. Report-only information grouping and VME advice live here so scoring stays unchanged. Snapshots with `v23` render through `Report23`/`quickscanPdf23` with optional versioned extensions (`v232`, `v233`, `v234`) and no recomputation; snapshots without an extension keep their original render path, and older snapshots keep the legacy view/PDF. PDF dispatch is per stored version: 2.3.4 uses `pdf/render234.ts` (premium cover), 2.3.3 uses `render233.ts`, older use `historical-frozen.ts`; browser and server mail must use the same versioned renderer.
- Quickscan questions may define `optionsFor(answers)` for dynamic option lists (e.g. primary heating limited to selected systems); UI and server validation both resolve options through `questionOptions()`, and legacy scalar answers are normalized before the resolver runs.
- The Quickscan report number may travel in URLs (`?rapport=`) only as a reference in a request; it never grants access to report content or personal data.
- Quickscan question visibility is resolved by the bounded fixpoint resolver in `engine.ts` (throws `ResolverError` on non-convergence; `isComplete()` fails closed), and the questionnaire tracks the current question by ID so newly activated earlier questions are asked afterwards, never by jumping.
- Legal/EPC/asbestos facts live only in `_shared/quickscan/legal.ts` with a source URL and verification date; reports cite them and never compute personal deadlines.
- PDF snapshot layout lives in runtime-neutral `_shared/quickscan/pdf` with injected assets and formatting; browser adapters dispatch by stored report version, keeping historical rendering frozen and strict server asset validation so mail never silently substitutes fonts or omits the logo. Frozen local history is not proof of original release provenance.
- Local PDF adapters load managed public project assets from their hosted origin because Vite's fallback HTML is not a valid font; production assets and historical renderers stay unchanged.
- User-facing information coverage is a report-only additive extension; never use it as a scoring or product-routing input, so more truthful display levels cannot change recommendations.
- Version 2.3.4 browser and PDF presentation share `presentation234.ts`, which clones stored prose without recalculation; historical versions bypass it so editorial changes never mutate snapshots or decisions.
- Legacy delivery preparation uses dependency-injected worker ports and a non-applied SQL proposal under docs; absent provider/database adapters keep it inactive until separately approved configuration and migration. Ambiguous provider outcomes require reconciliation rather than blind retry.
- Legal pages share LegalPage and frontend-only policy constants; prices are read from the existing catalog, and legal display values must never trigger billing, deletion or alter Quickscan decisions.
- Original media copies sit beside their `.asset.json` pointers in `src/assets` for GitHub export; keep pointers and runtime imports unchanged to protect existing pages and historical PDFs.
